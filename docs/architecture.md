# OrkoPay architecture

## Components

```
                    ┌──────────────────────┐
  checkout page ──▶ │  OrkoNet API         │── creates invoice (pending)
                    │  (invoices table)    │◀─ reads status, releases order
                    └─────────▲────────────┘
                              │ UPDATE status
                    ┌─────────┴────────────┐
                    │  orkopay-indexer     │  polls logs, N confirmations
                    └─────────▲────────────┘
                              │ PaymentReceived / OrderRefunded
 customer wallet ─deposit()─▶ ┌──────────────────────┐   isActive / tier / payout
                              │  OrkoPay             │──────────────▶ OrkoPayRegistry
 merchant ──withdraw()──────▶ │  balances per asset  │                 (owner: ops multisig,
 merchant/ops ──refund()────▶ │  accrued fees        │                  operators: onboarding)
 finance ──collectFees()────▶ └──────────────────────┘
```

## Order lifecycle

| On-chain status | Invoice status (DB) | Trigger |
|---|---|---|
| `None` | `pending` | Invoice created by the API |
| `Paid` | `paid` / `underpaid` | `deposit` / `depositToken`, confirmed by indexer |
| `Refunded` | `refunded` | `refund`, confirmed by indexer |
| — | `expired` | API job after `expires_at` with no payment |

`orderId` is `keccak256(invoiceId)`. Invoice IDs are UUIDv4 generated by the API,
so order IDs are unique per invoice and not guessable before checkout.

## Accounting

For every asset `a`:

```
asset held by OrkoPay == Σ merchant balances[a] + accruedFees[a]
```

This is enforced by `test/invariant/OrkoPay.invariant.t.sol` for ETH.

- **Payment:** `balances[merchant] += net`, `accruedFees += fee`.
- **Withdrawal:** `balances[merchant] -= amount`, transfer to payout.
- **Refund:** `balances[merchant] -= net`, `accruedFees -= fee`, transfer gross
  to customer. Refunds are funded from the merchant's unwithdrawn balance;
  merchants that withdraw immediately must top up via support for refunds.
- **Fee sweep:** `accruedFees = 0`, transfer to fee recipient.

## Roles and trust model

| Role | Holder | Can |
|---|---|---|
| Owner | Ops multisig (3-of-5) | Fees, registry pointer, assets, pause, payout changes, refunds |
| Operator | Onboarding service | Register merchants, set status and tier |
| Fee recipient | Treasury Safe | Sweep fees |
| Merchant | Merchant operating key | Withdraw own balance, refund own orders |

The owner is trusted: it can redirect a merchant's payout address and replace
the registry. Operator keys live in the onboarding service and are considered
lower-trust, which is why payout changes are owner-only.

## Design decisions

- **Pull payments.** Merchants withdraw rather than being paid inline, so a
  broken payout address cannot block customer checkouts.
- **Pause scope.** Pausing stops new payments only. Withdrawals and refunds
  always work so funds are never frozen.
- **Allowlisted tokens.** Only plain ERC-20s (USDC) are enabled. Fee-on-transfer
  and rebasing tokens are not supported by the accounting model.
- **Non-upgradeable.** Breaking changes ship as a new deployment plus a
  registry/indexer migration. See CONTRIBUTING.md.
- **Vendored utils.** Ownable2Step, Pausable and ReentrancyGuard are adapted
  from OpenZeppelin v5 and kept in-tree so the audited surface is pinned.
